Features

Everything you need. Nothing you don't.

Native SDKs for Python and Node.js, OpenTelemetry for everything else — not a generic agent with a per-host bill. Read the docs →

One line of instrumentation
No decorators, no manual spans. Routes are recorded as templates (/users/{id}), never raw paths. The release is picked up from your CI or host automatically.
import reqly app = FastAPI() # or Flask, Starlette, Litestar reqly.instrument(app, service_name="checkout-api") # Django: add "reqly.integrations.django.ReqlyMiddleware" # any WSGI/ASGI app: reqly.instrument_wsgi(app, route_resolver=...)
import { reqlyExpress } from "reqly-node"; app.use(reqlyExpress({ serviceName: "checkout-api" })); // Fastify: app.register(reqlyFastify({ ... })) // Hono: app.use(reqlyHono({ ... })) // Koa: app.use(reqlyKoa({ ... })) NestJS: reqlyNest(app, { ... })
# any OpenTelemetry SDK — exporter settings only OTEL_EXPORTER_OTLP_ENDPOINT=https://reqly.example.com/otlp OTEL_EXPORTER_OTLP_HEADERS=x-reqly-key=rqk_... OTEL_SERVICE_NAME=checkout-api
Fail-open and cheap
SDK errors never reach your app, and a dead collector adds no latency.
  • Shipping in the background, batched
  • Bounded queue; retries 408 / 429 / 5xx
  • ~6–33 µs per request, benchmarked
  • No request bodies, query strings or headers
Percentiles that are right
Per-route sketches merge exactly across routes and time, so a 7-day service p95 is a real p95 — not the max of per-minute ones.

Root cause, not just charts

Knows what changed

Every anomaly comes with the release that was running and where the errors are concentrated — computed from your data, not guessed by a model. How alerts work →

Deploy-aware
Every event carries its release (from GITHUB_SHA, RENDER_GIT_COMMIT, …). Regressions show the release they started on, with before → after numbers.
Seasonal baseline
Each hour is compared with the same weekday-hour over 8 weeks. One alert per route, reminders while it fires, a resolve message when it's over.
Root-cause leads
Errors concentrated on one host, environment, status code or error type relative to its traffic share — surfaced in alerts and reports.
Who it hit
With consumer tracking on, each alert lists the API clients affected, so you know who to tell before they tell you.

Ask Reqly

Ask why, in plain English

Not text-to-SQL: the model can only call nine read-only query tools, and its answer is checked against what they returned. Ask Reqly docs →

Answers you can verify

Ask about one service — latency, errors, releases, alerts, SLOs, drift, consumers or LLM cost. The dashboard shows each query the model ran next to the answer.

  1. 1You ask a question about a service
  2. 2The model picks from 9 read-only tools — at most 6 calls
  3. 3Tools return rounded aggregates, never raw events or SQL
  4. 4Every number in the answer is matched against the tool results; anything unmatched is flagged
Why did /orders start failing on Friday?
Errors on /orders rose to 30.0% between 15:00 and 16:00 UTC, against a usual 2.2%. Release v2 was running — compared with v1, errors went from 2.6% to 33.1% — and all of them came from host pod-3, which served 23% of the traffic.

Stack

Deliberate technology choices

Every layer has a reason. No bloat, no magic.

LayerTechnology & reason
SDKsPython 3.9+ — pure ASGI/WSGI middleware, httpx, background thread · Node.js 20+ — TypeScript, zero dependencies, ESM + CJS · OTLP/HTTP for everything else
CollectorFastAPI · asyncpg · APScheduler · Pydantic v2 · argon2 — async throughout, no ORM; native ingest plus an OTLP receiver
DatabaseTimescaleDB (pg16, Toolkit) — hypertables, continuous aggregates, UddSketch percentiles
DashboardReact 19 · Vite · TypeScript · Tailwind CSS 4 · Recharts · TanStack Query
AIGroq · gpt-oss-120b with tool calling — statistics first, the LLM explains and answers only from query results
InfraDocker Compose · prebuilt images on GHCR (amd64 + arm64) · PyPI and npm trusted publishing · optional AWS Lambda for the weekly job
